1. Interface declarativa com Compose

@Composable

anotação do Jetpack Compose

É a anotação que transforma uma função Kotlin comum numa "peça de interface". Em vez de montar a tela imperativamente (criar um botão, depois adicionar ele na tela, depois configurar o clique), a gente só descreve "como a tela deveria ser" pro estado atual, e o Compose desenha isso sozinho.

Toda tela do projeto (FeedScreen, LoginScreen etc.) e todo componente reaproveitado (CardPost, TopNavBar) é uma função marcada com @Composable.

@Composable
fun CardPost(username: String, ...) {
    Card(...) { ... }
}

Sempre que algum dado que a função usa muda, o Compose chama a função de novo (isso se chama "recomposição") e só atualiza na tela o que realmente mudou.

2. Estado da tela

remember e mutableStateOf

androidx.compose.runtime

mutableStateOf(valorInicial) cria uma "caixinha" de estado: um valor que, quando muda, avisa o Compose pra redesenhar quem está usando ele. remember { ... } garante que esse valor não seja recriado do zero toda vez que a função for recomposta, ele "lembra" o valor entre recomposições.

var email by remember { mutableStateOf("") }

Usado em praticamente toda tela com campo de texto (LoginScreen, RegisterScreen, PostScreen) pra guardar o que o usuário está digitando.

No projeto: campos de formulário, controle de "senha visível/escondida" no LoginScreen, e o id do post aguardando confirmação de exclusão no FeedScreen.

O operador "by" (property delegation)

recurso da linguagem Kotlin

Sem o by, pra usar o valor de dentro de um mutableStateOf seria preciso escrever email.value toda vez. Com by, o Kotlin "delega" a leitura e escrita da variável direto pro mutableStateOf, então email se comporta como uma String normal.

var loading by mutableStateOf(false)
    private set

Esse private set aparece em quase todo ViewModel do projeto: qualquer código pode ler o valor, mas só o próprio ViewModel pode alterá-lo. É assim que a tela nunca consegue mudar o estado "por fora", só através de uma função do ViewModel.

LaunchedEffect

androidx.compose.runtime

Roda um bloco de código suspenso (uma coroutine) quando a tela aparece, e roda de novo toda vez que a "chave" passada pra ele mudar. É a forma correta, dentro do Compose, de reagir a mudanças de estado ou disparar uma ação uma única vez.

LaunchedEffect(Unit) {
    postViewModel.list()
}

Com a chave Unit (que nunca muda), o bloco roda uma única vez, quando a tela é exibida pela primeira vez. É assim que o FeedScreen busca os posts assim que abre.

LaunchedEffect(authViewModel.done) {
    if (authViewModel.done) {
        authViewModel.consumeResult()
        onLoginSuccess()
    }
}

Já aqui, a chave é o próprio estado done. Toda vez que ele mudar (de false pra true, quando o login dá certo), o bloco roda de novo e navega pro feed. É o mesmo mecanismo usado pra exigir login: em AppNavigation.kt, um LaunchedEffect(destination, currentUser) redireciona pro Login sempre que alguém tenta abrir uma rota protegida sem estar logado.

3. Listas

LazyColumn e items

androidx.compose.foundation.lazy

É a versão "preguiçosa" (lazy) de uma coluna com rolagem. A diferença pra uma Column normal dentro de um scroll é que a LazyColumn só desenha na memória os itens que estão realmente visíveis na tela (mais uma pequena margem), em vez de desenhar os 500 posts do banco de uma vez. Isso é essencial pra performance de uma lista que pode crescer bastante, como o feed.

LazyColumn {
    item { CircularProgressIndicator() }
    items(postViewModel.posts, key = { it.id }) { post ->
        CardPost(...)
    }
}

item { } adiciona um elemento único (tipo um cabeçalho). items(lista, key = ...) adiciona um elemento pra cada posição da lista. O parâmetro key ajuda o Compose a saber "qual item é qual" mesmo que a lista seja reordenada, evitando redesenhar tudo à toa.

Usado no Feed, no Perfil (lista de posts do usuário) e na tela de Seguidores/Seguindo.

rememberSaveable

androidx.compose.runtime.saveable

Igual ao remember, mas sobrevive também a uma troca de configuração do sistema (como girar a tela), porque o valor é salvo num Bundle, não só em memória. Usado pra guardar qual post está aguardando confirmação de exclusão, pra não perder esse estado se o usuário girar o celular no meio da confirmação.

var deleteId by rememberSaveable { mutableStateOf<Long?>(null) }

4. ViewModel e coroutines

ViewModel e AndroidViewModel

androidx.lifecycle

Um ViewModel é uma classe que guarda o estado de uma tela de um jeito que sobrevive a recomposições e a mudanças de configuração (como girar o celular), porque ele não é recriado junto com a tela, ele fica "amarrado" ao ciclo de vida da tela/rota, não ao desenho dela.

AndroidViewModel é um ViewModel que já recebe o Application (contexto da aplicação) no construtor, necessário aqui porque os DAOs (UserDAO, PostDAO...) precisam de um Context pra abrir o banco.

class PostViewModel(application: Application)
    : AndroidViewModel(application) {
    private val dao = PostDAO(application)
    var posts by mutableStateOf<List<Post>>(emptyList())
        private set
    ...
}

A tela pega uma instância dele assim: postViewModel: PostViewModel = viewModel(). O Compose cuida de criar e reaproveitar essa instância sozinho.

viewModelScope e coroutines (launch)

androidx.lifecycle / kotlinx.coroutines

Uma coroutine é uma forma de rodar código que pode "pausar" (por exemplo, esperando o banco responder) sem travar a interface do usuário enquanto espera. viewModelScope é um escopo de coroutine que já é cancelado automaticamente se o ViewModel for destruído, evitando vazamento de tarefa rodando à toa.

viewModelScope.launch {
    try {
        done = withContext(Dispatchers.IO) { op() }
    } catch (e: Exception) {
        message = "Ocorreu um erro inesperado."
    } finally {
        loading = false
    }
}

Esse padrão (função run privada dentro de cada ViewModel) se repete em AuthViewModel, PostViewModel, ProfileViewModel e FollowsViewModel: controla o loading, roda a operação, e transforma qualquer erro numa mensagem amigável pra tela mostrar.

Dispatchers.IO e withContext

kotlinx.coroutines

Acessar o banco de dados é uma operação de entrada/saída (I/O) que pode demorar uns milissegundos. Se isso rodasse na thread principal (a que desenha a tela), o app congelaria por um instante. Dispatchers.IO é um grupo de threads feito pra esse tipo de tarefa.

withContext(Dispatchers.IO) {
    dao.create(userId, trimmedContent)
}

withContext troca pra essa thread só durante o bloco, executa o código ali, e volta pra thread principal automaticamente assim que termina, já com o resultado pronto pra atualizar o estado da tela com segurança.

5. Navegação entre telas

NavHost, NavController e rotas @Serializable

androidx.navigation.compose

NavController é o objeto que sabe pra onde o app está navegando e guarda o histórico de telas (pra o botão "voltar" funcionar). NavHost é o componente que declara todas as rotas possíveis e qual tela corresponde a cada uma.

Cada rota é uma classe ou objeto Kotlin marcado com @Serializable, em vez de uma simples String como em projetos mais antigos. Isso dá segurança de tipos: é impossível, por exemplo, navegar pra tela de detalhe do post esquecendo de informar o postId, porque isso nem compila.

@Serializable
data class DetailPost(val postId: Long)

// ...
composable<DetailPost> { backStackEntry ->
    val rota = backStackEntry.toRoute<DetailPost>()
    DetailPostScreen(postId = rota.postId, ...)
}

Pra navegar, só se cria uma instância da rota: navController.navigate(DetailPost(post.id)).

Scaffold e TopAppBar

androidx.compose.material3

Scaffold é um "esqueleto" de tela padrão do Material Design: já reserva o espaço certo pra uma barra do topo, conteúdo e eventualmente uma barra inferior, cuidando do espaçamento (innerPadding) sozinho. No projeto existe um único Scaffold, lá no MainActivity, que envolve a navegação inteira.

Scaffold(
    topBar = { if (showTopBar) TopNavBar(navController) }
) { innerPadding ->
    AppNavigation(modifier = Modifier.padding(innerPadding))
}

TopAppBar (usado dentro do TopNavBar) é a barra fixa no topo com o nome do app e os ícones de ação (novo post, feed, perfil, sair). Ela só aparece quando a rota atual não é Login nem Cadastro.

AlertDialog

androidx.compose.material3

Uma janela de confirmação que flutua por cima do resto da tela. Usada sempre que uma ação é irreversível, como excluir um post: em vez de excluir no primeiro clique, o botão "Excluir" só marca qual item deveria ser excluído, e o AlertDialog pede confirmação antes de chamar o ViewModel de verdade.

AlertDialog(
    onDismissRequest = { deleteId = null },
    title = { Text("Excluir post?") },
    confirmButton = {
        TextButton(onClick = {
            deleteId = null
            postViewModel.delete(post.id)
        }) { Text("Excluir") }
    },
    dismissButton = {
        TextButton(onClick = { deleteId = null }) { Text("Cancelar") }
    }
)

6. Banco de dados

SQLiteOpenHelper

android.database.sqlite

É a classe base do Android pra criar e manter um banco SQLite, sem precisar de nenhuma biblioteca externa (nada de Room). Se estende essa classe e implementa dois métodos: onCreate (roda só na primeira vez que o app abre, cria todas as tabelas do zero) e onUpgrade (roda quando o número de versão do banco aumenta, aplica as mudanças de schema nos dados que já existem).

class AppDatabase(context: Context) : SQLiteOpenHelper(
    context.applicationContext,
    File(context.noBackupFilesDir, "mysocial.db").absolutePath,
    null,
    2 // versão do schema
) {
    override fun onCreate(db: SQLiteDatabase) { ... }
    override fun onUpgrade(db, oldVersion, newVersion) { ... }
}

writableDatabase abre o banco em modo leitura e escrita (usado pra INSERT/UPDATE/DELETE). readableDatabase abre só pra leitura (usado nas buscas). Os DAOs sempre usam AppDatabase(context).use { db -> ... }, o use garante que a conexão é fechada sozinha ao final, mesmo se der erro no meio.

ContentValues e Cursor

android.content / android.database

ContentValues é um mapa de "nome da coluna" para "valor", usado pra montar um INSERT ou UPDATE sem concatenar texto (o que abriria brecha pra SQL Injection).

val values = ContentValues().apply {
    put("username", username)
    put("email", email)
}
db.writableDatabase.insertOrThrow("users", null, values)

Cursor é o objeto que representa o resultado de uma consulta (query ou rawQuery), uma linha por vez. cursor.moveToNext() avança pra próxima linha, e cursor.getLong(0)/getString(1) leem o valor de cada coluna pela posição.

db.readableDatabase.query(
    "users", arrayOf("id", "username", "email"),
    "id = ?", arrayOf(id.toString()),
    null, null, null
).use { cursor ->
    if (cursor.moveToFirst())
        User(cursor.getLong(0), cursor.getString(1), cursor.getString(2))
    else null
}

Repare no "id = ?" com arrayOf(id.toString()) logo depois: esse é o "bind parameter". O SQLite substitui o ? pelo valor de forma segura, nunca interpretando o conteúdo como parte do comando SQL. É assim que todo o projeto se protege de SQL Injection.
